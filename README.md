# AI Chat Bot — سكيلتون المشروع

بوت خدمة عملاء بالذكاء الاصطناعي، متعدد العملاء (multi-tenant)، يشتغل على قناتين:
- **ودجت شات على موقع العميل** (`src/widget/chat-widget.js`)
- **واتساب** عبر WhatsApp Cloud API

المحرك: DeepSeek API. القدرات الجاهزة: **تسجيل ذاتي** (شركة تسجّل حالها بنفسها بدون أي تدخل منك)، تصعيد لإنسان، استيراد قاعدة معرفة من PDF/إكسل/موقع، حجز مواعيد، وذاكرة دائمة لكل زبون.

## التشغيل المحلي

```bash
npm install
cp .env.example .env
```

عبّي `.env`: على الأقل `DEEPSEEK_API_KEY` عشان تجرب الودجت محليًا. واتساب وSMTP اختياريين لحد ما تكون جاهز تربطهم.

```bash
npm run dev
```

افتح `http://localhost:3000/widget/chat-widget-demo.html` وجرب تحكي مع البوت (عميل `example-client` اليدوي).

## طريقتين لإضافة عميل

### أ) تسجيل ذاتي (الشركة بتعمل حالها — الطريقة الافتراضية الآن)

فعّل `SIGNUP_ENABLED=true` بـ `.env`، وابعت الشركة على `http://your-server/public/signup.html`. أربع خطوات بدون أي تدخل منك:

1. **التسجيل** — اسم الشركة، إيميل، رقم واتساب للتنبيهات، رقم تصعيد، رابط الموقع.
2. **تأكيد الإيميل** — رابط بالإيميل (أو يطبع بالـ `console` لو ما عندك SMTP بعد — وضع تطوير كافي تجرب فيه الفلو كامل).
3. **رفع المعرفة** — ملف PDF/إكسل أو "استورد من موقعي". بينعمل فحص جودة تلقائي (`ingest.sanityCheck`) قبل ما يوصل لأي إنسان، وبتقدر الشركة تجرّب بوتها مباشرة (`preview-chat`) قبل ما تفعّل.
4. **التفعيل** — كود الودجت الجاهز يلصقوه بموقعهم فورًا.

العميل بيتولد بحالة `preview` (مش قابل للرد على زبائن حقيقيين) لحد ما تنضغط "تفعيل"، وبعدها بفترة تجريبية (`TRIAL_DAYS`, افتراضي 14 يوم) بسقف رسائل (`TRIAL_MESSAGE_CAP`) — لو خلصت الفترة أو السقف، البوت بيوقف تلقائيًا (`registry.isServable`).

بيوصلك إشعار واتساب (`OPERATOR_WHATSAPP`) عند كل تفعيل. راقب `data/signups/` و`src/clients/<id>/config.json` (حقل `knowledgeReviewed: false`) لمراجعة عملاء جدد لاحقًا.

### ب) يدوي (زي قبل — لعملاء واتساب أو مواعيد)

1. انسخ `src/clients/example-client` (أو `example-clinic` لو بدك حجز مواعيد) لمجلد جديد باسم العميل.
2. عدّل `config.json`: `id` (لازم يطابق اسم المجلد)، `displayName`، `tone`، `escalation`.
3. اكتب معلومات العميل بـ `knowledge.md` — أو استوردها: `npm run ingest -- <clientId> pdf|excel|website <مصدر> [اسم]`.
4. لربط الموقع: حط سكربت `chat-widget.js` بآخر `<body>`، مع `data-public-key` (صدّره بـ `npm run key -- issue <clientId> --type=public` — أداة لسا لازم تُبنى، لهلق عدّل `auth.json` يدويًا أو استخدم `data-widget-key` القديم).
5. لربط واتساب: راجع قسم "ملكية رقم واتساب" تحت (التسجيل الذاتي حاليًا widget-only، ما بيربط واتساب تلقائيًا).

## المصادقة: pk_ (عام) مقابل sk_ (سري)

- **`pk_...`** — بيروح بالودجت المُضمّن بموقع الشركة، ظاهر لأي حدا يفتح مصدر الصفحة. حمايته بحصر الأصل (`allowedOrigins`) وحد المعدل، مو بالسرية. هو يلي التسجيل الذاتي بيصدّره تلقائيًا بالخطوة ٣.
- **`sk_...`** — سيرفر-لسيرفر بس (مثلاً شركة بتجيب بياناتها من سيرفرها هي)، مُخزّن مُشفّر (`auth.json`)، أبدًا نص صريح. ما في endpoint بيستخدمه لسا (appointments/usage APIs مؤجّلة لحد أول عميل يطلبها فعليًا).
- **الوضع القديم (`x-widget-key` + `WEB_WIDGET_KEY`)** — لسا شغال لأي عميل يدوي قديم (`ALLOW_LEGACY_WIDGET_KEY=true`). راقب `console.warn` بصيغة `[auth] عميل "..." لسا عم يستخدم...` لتعرف مين لازم يترحّل، وبعدين طفّي المتغير.

## استيراد قاعدة معرفة يدويًا (`scripts/ingest.js`)

```bash
npm run ingest -- <clientId> pdf "C:\path\catalog.pdf" catalog
npm run ingest -- <clientId> excel "C:\path\products.xlsx" products
npm run ingest -- <clientId> website "https://client-site.com/faq" faq
```

كل أمر بيكتب `src/clients/<clientId>/source-<اسم>.md`، و`registry.js` بيلزقه تلقائيًا مع `knowledge.md`. راجع الملف الناتج قبل ما تعتمد عليه — خصوصًا PDF (النص المستخرج ممكن يجي مبعثر، وpdf-parse مكتبة قديمة نسبيًا). التسجيل الذاتي بيستخدم نفس المنطق (`src/services/ingest.js`) بس محاط بفحص جودة تلقائي (`sanityCheck`) وحماية SSRF (`urlGuard`) لأنه مصدره مستخدم خارجي، مو إنت.

⚠️ **موقع محتواه Javascript-rendered** (منيو/كتالوج بيتحمّل ديناميكيًا بـReact/Vue بعد تحميل الصفحة، شائع بمواقع المطاعم الحديثة): الاستيراد بيجيب الـHTML الخام بس، بدون تشغيل جافاسكريبت، فبيرجع نص فاضي أو ناقص (عناصر تنقّل، بدون المحتوى الفعلي). `sanityCheck` بيرفض النص القصير جدًا تلقائيًا، بس لو رجع نص "شكله معقول" بس ناقص (زي صفحة دليل مطاعم فيها أرقام تواصل بس بدون قائمة الطعام الفعلية)، ما في طريقة تلقائية تكتشفها — راجع المعاينة (`previewExcerpt`) بخطوة onboard.html قبل التفعيل. الحل الأضمن لموقع كهيك: ملف PDF أو إكسل بدل الموقع.

**قاعدة بيانات العميل** (SQL/Firebase/إلخ): مو مدعومة بأداة عامة لأن كل قاعدة مختلفة الشكل. اكتب سكربت تصدير بسيط يفرّغ الجداول المهمة كـ CSV، ومرّره بنمط `excel`.

⚠️ لو قاعدة المعرفة كبرت كتير (أكثر من ~60 ألف حرف)، `sanityCheck` بيرفضها تلقائيًا للتسجيل الذاتي — حقنها كاملة بكل رسالة رح يصير غالي وبطيء. هاي أول إشارة حقيقية للانتقال لـ RAG حقيقي (تقسيم + بحث دلالي).

## التصعيد لإنسان

يشتغل نفس الشي عالودجت وعالواتساب:
- لو الزبون كتب كلمة من قائمة `ESCALATION_KEYWORDS` بـ `src/services/handoff.js` (عدّلها حسب اللهجة المتوقعة)، البوت بيرد فورًا برسالة تحويل بدون حتى ما يستدعي DeepSeek.
- أو لو الذكاء الاصطناعي نفسه قرر إنه ما فيه يساعد، بيضيف ماركر داخلي بآخر رده وبتصير نفس العملية.
- بالحالتين: المحادثة "توقف" (`HANDOFF_PAUSE_HOURS`، افتراضي 4 ساعات)، وبيتبعت إشعار واتساب لصاحب العمل على `escalation.notifyWhatsapp` تبعه (يحتاج `NOTIFY_WHATSAPP_PHONE_NUMBER_ID` مُعرّف — رقم "مُرسل" مسجّل عندك بـ Meta).
- **حدود معروفة**: ما في لوحة تحكم يرد منها صاحب العمل مباشرة — الإشعار بس بيلفت نظره. لواتساب تحديدًا، فيه ميزة **WhatsApp Coexistence** من Meta (رقمه يشتغل بتطبيق WhatsApp Business العادي وCloud API بنفس الوقت) ما ركّبناها بعد.

## حجز المواعيد

فعّلها لعميل بإضافة `appointments` بـ `config.json` تبعه (شوف `example-clinic`):

```json
"appointments": {
  "enabled": true,
  "workingHours": { "start": "09:00", "end": "17:00" },
  "slotMinutes": 30,
  "offDays": [5]
}
```

`offDays`: 0=أحد … 6=سبت. البوت بيصير عنده أداتين (`check_availability`/`book_appointment` عبر function calling). التخزين بملف JSON بسيط — لا يدعم إلغاء/تعديل موعد لهلق (أضف `cancel_appointment` بنفس نمط `book_appointment` بـ `deepseek.js` لو احتجتها). التسجيل الذاتي حاليًا **ما بيفعّل مواعيد تلقائيًا** — عميل صار يحتاجها بيضيفها إنت يدويًا.

⚠️ **`workingHours` واحدة لكل الأيام المفتوحة** — لا يدعم ساعات مختلفة حسب اليوم (مثلاً عيادة حقيقية اختبرناها فيها الثلاثاء لحد 7م وباقي الأيام لحد 6م). لعميل بساعات متغيّرة، خذ **أضيق نطاق مشترك** (هون: 9-6) حتى ما توعد بوقت مو موجود فعليًا — تحت-عرض التوفر آمن، فوق-عرضه مو آمن. توسيع الـschema لساعات لكل يوم تحسين مستقبلي لو احتجته.

## ذاكرة الزبون (آخر سؤال + تفضيلات)

كل زبون إله ملف دائم بـ `data/<clientId>/customers/<userId>.json` (تاريخ محادثة + `facts` يقرر البوت بنفسه حفظها عبر أداة `remember_customer_fact`). أقصى 20 معلومة محفوظة لكل زبون. ما في إعداد إضافي مطلوب.

## كاش الردود (توفير تكلفة DeepSeek)

أسئلة FAQ متكررة الصياغة (نفس السؤال بترقيم/مسافات مختلفة) بتترد من الكاش مباشرة بدون استدعاء DeepSeek — `src/services/replyCache.js`، بذاكرة السيرفر (مو ملف)، TTL افتراضي 12 ساعة (`REPLY_CACHE_TTL_HOURS`) وحد أقصى 500 عنصر (`REPLY_CACHE_MAX_ENTRIES`). طفّيه بـ `REPLY_CACHE_ENABLED=false` لو احتجت.

**نطاق آمن ضيق عمدًا** — الرد ينخزّن/ينسترجع بس لو الثلاثة شروط مجتمعة:
1. الزبون "أول تواصل" (بدون تاريخ محادثة ولا معلومات محفوظة عنه) — حتى ما ينسرب سياق زبون تاني.
2. الرد ما استخدم أي أداة (حجز، فحص توفر، تذكّر معلومة) — حتى ما نخزّن جواب مرتبط بلحظة زمنية أو بزبون محدد.
3. الرد بدون تصعيد — حتى ما نعيد إطلاق إشعار تلقائي بكل cache hit.

يعني عمليًا: أسئلة عامة ("شو ساعات الدوام؟"، "وين عنوانكم؟") بتتخزّن، وأي شي فيه حجز/سعر/توفر لحظي ما بيتخزّن أبدًا — التحقق شغال حي، الفرق قياسًا: ~5ms (كاش) مقابل ~2000ms (استدعاء DeepSeek فعلي).

## ملكية رقم واتساب — مين بيعطي شو

الرقم لازم يكون مسجّل تحت WhatsApp Business Account (WABA) بمنصة Meta:

1. **الأسرع للبداية**: تسجّل رقم العميل تحت Business Manager تبعك إنت — بس بيعطيك رقم مخصص، وتحط `phone_number_id` الناتج بـ `config.json` تبعه يدويًا.
2. **أنضف على المدى الطويل**: العميل يسوي حساب Meta Business Manager تبعه هو ويعطيك صلاحية وصول (embedded signup).

ابدأ بالطريقة 1 لأول 3-5 عملاء (حساب غير موثّق كافي لـ 250 محادثة/24 ساعة). التسجيل الذاتي widget-only حاليًا — ربط واتساب لعميل تسجّل حاله ذاتيًا لسا خطوة يدوية.

## نشر السيرفر (deploy)

يشتغل على أي مكان يستضيف Node.js (Railway، Render، VPS رخيص). لازم HTTPS ثابت + `PUBLIC_BASE_URL` مضبوط صح (بيروح براوابط تأكيد الإيميل وكود الودجت الجاهز).

## ملاحظات أمان قبل أول عميل حقيقي

- `.env` وملفات `data/` (فيها `signups/`, `customers/`, `appointments.json`) ما بينرفعوا لأي مكان (`.gitignore`) — فيها بيانات شخصية حقيقية.
- `WEB_WIDGET_KEY`/الوضع القديم مو أمان حقيقي (ظاهر بمصدر الصفحة) — استبدله بـ `pk_` لكل عميل أول ما تقدر.
- `urlGuard.js` بيمنع SSRF (روابط داخلية/محجوزة) لما "استورد من موقعي" بيجيب رابط من مستخدم خارجي — حد معروف: نافذة نظرية لـ DNS rebinding (راجع تعليقات الملف).
- مكتبة `xlsx` الأصلية عندها ثغرات أمنية بدون حل — استبدلناها بـ `exceljs`. تحذير moderate متبقي بتبعية `uuid` غير مباشرة (نمط استخدام غير مرتبط بيلي عنا).
- **قبل ما توصل بوت لأول عميل حقيقي**: راجع نقطة "الهلوسة والمسؤولية القانونية" من قرار المجلس (`council-report-20260804-225516.html` بمجلد `new app work`) — حط بند تعاقدي واضح يحدد مين مسؤول عن غلطة البوت. للعملاء اللي بيجوا عبر التسجيل الذاتي تحديدًا: `knowledgeReviewed: false` وتحذير بالـ system prompt بيقللوا الخطر (البوت بيصعّد بدل ما يخمّن)، بس مو بديل كامل عن المراجعة.

## معروف ناقص (مؤجّل عمدًا)

- **`/docs`**: مسار مُركّب بالسيرفر بس فاضي — توثيق API رسمي (OpenAPI + Redoc/Scalar) لسا لازم يُبنى. مو ضروري لحد أول شركة تطلب تكامل برمجي مباشر (مو بس الودجت الجاهز).
- **`npm run key`**: أداة CLI لإصدار/سحب مفاتيح `sk_`/`pk_` لعملاء يدويين — لهلق عدّل `auth.json` بمجلد العميل يدويًا (`{ "publicKey": "pk_...", "apiKeys": [] }`).
- **`sk_` endpoints** (`/appointments`, `/usage`): مؤجّلة لحد أول عميل يطلب وصول برمجي فعلي لبياناته.
