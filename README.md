# AI Chat Bot — سكيلتون المشروع

بوت خدمة عملاء بالذكاء الاصطناعي، متعدد العملاء (multi-tenant)، يشتغل على قناتين:
- **ودجت شات على موقع العميل** (`src/widget/chat-widget.js`)
- **واتساب** عبر WhatsApp Cloud API

المحرك: DeepSeek API. القدرات الجاهزة: **تسجيل ذاتي** (شركة تسجّل حالها بنفسها بدون أي تدخل منك)، تصعيد لإنسان، استيراد قاعدة معرفة من PDF/إكسل/موقع، حجز مواعيد، وذاكرة دائمة لكل زبون.

## التشغيل المحلي

```bash
npm install
cp .env.example .env
```

عبّي `.env`: على الأقل `DEEPSEEK_API_KEY` + قسم **Firebase كامل** (مطلوب للإقلاع — حسابات المستخدمين وطلبات التسجيل والعدادات بـFirestore). `META_APP_SECRET` صار إلزامي لشغل ويبهوك واتساب (تحقق توقيع). واتساب نفسه اختياري للتجربة المحلية.

```bash
npm run dev
```

اختبارات:

```bash
npm test            # اختبارات وحدة سريعة (node --test) — مجانية، ما بتلمس أي API خارجي
npm run test:smoke  # اختبار دخان تكاملي — يتطلب سيرفر شغال + مفاتيح حقيقية (بيعمل استدعاء DeepSeek مدفوع)
```

افتح `http://localhost:3000/widget/chat-widget-demo.html` وجرب تحكي مع البوت (عميل `example-client` اليدوي).

## طريقتين لإضافة عميل

### أ) تسجيل ذاتي (الشركة بتعمل حالها — الطريقة الافتراضية الآن)

فعّل `SIGNUP_ENABLED=true` بـ `.env`، وابعت الشركة على `http://your-server/`. الهوية عبر حساب Firebase (إيميل/كلمة سر أو Google)، والخطوات:

1. **إنشاء حساب + بيانات الشركة** — اسم الشركة، رقم واتساب للتنبيهات، رقم تصعيد، رابط الموقع.
2. **رفع المعرفة** — ملف PDF/إكسل أو "استورد من موقعي". بينعمل فحص جودة تلقائي (`ingest.sanityCheck`) قبل ما يوصل لأي إنسان، وبتقدر الشركة تجرّب بوتها مباشرة (`preview-chat`) قبل ما تفعّل.
3. **ربط واتساب** — WhatsApp Embedded Signup بضغطة زر (اختياري، يحتاج `META_APP_*` مضبوطة).
4. **التفعيل** — كود الودجت الجاهز يلصقوه بموقعهم فورًا.

العميل بيتولد بحالة `preview` (مش قابل للرد على زبائن حقيقيين) لحد ما تنضغط "تفعيل"، وبعدها بفترة تجريبية (`TRIAL_DAYS`, افتراضي 7 أيام) بسقف رسائل (`TRIAL_MESSAGE_CAP`) — لو خلصت الفترة أو السقف، البوت بيوقف تلقائيًا (`registry.isServable`).

بيوصلك إشعار واتساب (`OPERATOR_WHATSAPP`) عند كل تفعيل. راقب `src/clients/<id>/config.json` (حقل `knowledgeReviewed: false`) لمراجعة عملاء جدد لاحقًا.

### ب) يدوي (زي قبل — لعملاء واتساب أو مواعيد)

1. انسخ `src/clients/example-client` (أو `example-clinic` لو بدك حجز مواعيد) لمجلد جديد باسم العميل.
2. عدّل `config.json`: `id` (لازم يطابق اسم المجلد)، `displayName`، `tone`، `escalation`.
3. اكتب معلومات العميل بـ `knowledge.md` — أو استوردها: `npm run ingest -- <clientId> pdf|excel|website <مصدر> [اسم]`.
4. لربط الموقع: صدّر مفتاح عام بـ `npm run key -- issue <clientId> [label]` وحط سكربت `chat-widget.js` بآخر `<body>` مع `data-public-key` (الأداة بتطبعلك الكود الجاهز للنسخ).
5. لربط واتساب: إما Embedded Signup من صفحة onboard (لو SIGNUP_ENABLED)، أو راجع قسم "ملكية رقم واتساب" تحت.

## المصادقة: pk_ (عام) مقابل sk_ (سري)

- **`pk_...`** — بيروح بالودجت المُضمّن بموقع الشركة، ظاهر لأي حدا يفتح مصدر الصفحة. حمايته بحصر الأصل (`allowedOrigins`) وحد المعدل، مو بالسرية. هو يلي التسجيل الذاتي بيصدّره تلقائيًا بالخطوة ٣.
- **`sk_...`** — سيرفر-لسيرفر بس (مثلاً شركة بتجيب بياناتها من سيرفرها هي)، مُخزّن مُشفّر (`auth.json`)، أبدًا نص صريح. ما في endpoint بيستخدمه لسا (appointments/usage APIs مؤجّلة لحد أول عميل يطلبها فعليًا).
- **الوضع القديم (`x-widget-key` + `WEB_WIDGET_KEY`)** — لسا شغال لأي عميل يدوي قديم (`ALLOW_LEGACY_WIDGET_KEY=true`). راقب `console.warn` بصيغة `[auth] عميل "..." لسا عم يستخدم...` لتعرف مين لازم يترحّل، وبعدين طفّي المتغير.

## استيراد قاعدة معرفة يدويًا (`scripts/ingest.js`)

```bash
npm run ingest -- <clientId> pdf "C:\path\catalog.pdf" catalog
npm run ingest -- <clientId> excel "C:\path\products.xlsx" products
npm run ingest -- <clientId> website "https://client-site.com/faq" faq
```

كل أمر بيكتب `src/clients/<clientId>/source-<اسم>.md`، و`registry.js` بيلزقه تلقائيًا مع `knowledge.md`. راجع الملف الناتج قبل ما تعتمد عليه — خصوصًا PDF (النص المستخرج ممكن يجي مبعثر، وpdf-parse مكتبة قديمة نسبيًا). التسجيل الذاتي بيستخدم نفس المنطق (`src/services/ingest.js`) بس محاط بفحص جودة تلقائي (`sanityCheck`) وحماية SSRF (`urlGuard`) لأنه مصدره مستخدم خارجي، مو إنت.

⚠️ **موقع محتواه Javascript-rendered** (منيو/كتالوج بيتحمّل ديناميكيًا بـReact/Vue بعد تحميل الصفحة، شائع بمواقع المطاعم الحديثة): الاستيراد بيجيب الـHTML الخام بس، بدون تشغيل جافاسكريبت، فبيرجع نص فاضي أو ناقص (عناصر تنقّل، بدون المحتوى الفعلي). `sanityCheck` بيرفض النص القصير جدًا تلقائيًا، بس لو رجع نص "شكله معقول" بس ناقص (زي صفحة دليل مطاعم فيها أرقام تواصل بس بدون قائمة الطعام الفعلية)، ما في طريقة تلقائية تكتشفها — راجع المعاينة (`previewExcerpt`) بخطوة onboard.html قبل التفعيل. الحل الأضمن لموقع كهيك: ملف PDF أو إكسل بدل الموقع.

**قاعدة بيانات العميل** (SQL/Firebase/إلخ): مو مدعومة بأداة عامة لأن كل قاعدة مختلفة الشكل. اكتب سكربت تصدير بسيط يفرّغ الجداول المهمة كـ CSV، ومرّره بنمط `excel`.

⚠️ لو قاعدة المعرفة كبرت كتير (أكثر من ~60 ألف حرف)، `sanityCheck` بيرفضها تلقائيًا للتسجيل الذاتي — حقنها كاملة بكل رسالة رح يصير غالي وبطيء. هاي أول إشارة حقيقية للانتقال لـ RAG حقيقي (تقسيم + بحث دلالي).

## التصعيد لإنسان

يشتغل نفس الشي عالودجت وعالواتساب:
- لو الزبون كتب كلمة من قائمة `ESCALATION_KEYWORDS` بـ `src/services/handoff.js` (عدّلها حسب اللهجة المتوقعة)، البوت بيرد فورًا برسالة تحويل بدون حتى ما يستدعي DeepSeek.
- أو لو الذكاء الاصطناعي نفسه قرر إنه ما فيه يساعد، بيضيف ماركر داخلي بآخر رده وبتصير نفس العملية.
- بالحالتين: المحادثة "توقف" (`HANDOFF_PAUSE_HOURS`، افتراضي 4 ساعات)، وبيتبعت إشعار واتساب لصاحب العمل على `escalation.notifyWhatsapp` تبعه (يحتاج `NOTIFY_WHATSAPP_PHONE_NUMBER_ID` مُعرّف — رقم "مُرسل" مسجّل عندك بـ Meta).
- **حدود معروفة**: ما في لوحة تحكم يرد منها صاحب العمل مباشرة — الإشعار بس بيلفت نظره. لواتساب تحديدًا، فيه ميزة **WhatsApp Coexistence** من Meta (رقمه يشتغل بتطبيق WhatsApp Business العادي وCloud API بنفس الوقت) ما ركّبناها بعد.

## حجز المواعيد

فعّلها لعميل بإضافة `appointments` بـ `config.json` تبعه (شوف `example-clinic`):

```json
"appointments": {
  "enabled": true,
  "workingHours": { "start": "09:00", "end": "17:00" },
  "slotMinutes": 30,
  "offDays": [5]
}
```

`offDays`: 0=أحد … 6=سبت. البوت بيصير عنده ثلاث أدوات (`check_availability`/`book_appointment`/`cancel_appointment` عبر function calling). التخزين بملف JSON بسيط — **تعديل موعد** (نقل موعد محجوز لوقت تاني) هو الوحيد غير المدعوم. التسجيل الذاتي حاليًا **ما بيفعّل مواعيد تلقائيًا** — عميل صار يحتاجها بيضيفها إنت يدويًا (أو من لوحة الأدمن).

ساعات عمل مختلفة لكل يوم مدعومة الآن:

```json
"appointments": {
  "enabled": true,
  "workingHours": {
    "byDay": {
      "1": { "start": "09:00", "end": "18:00" },
      "2": { "start": "09:00", "end": "19:00" },
      "5": { "closed": true }
    }
  },
  "slotMinutes": 30,
  "offDays": []
}
```

مفاتيح `byDay` أرقام أيام JS (`getDay()`): 0=أحد … 6=سبت. اليوم بدون مدخل أو `closed:true` = مغلق، والساعات العامة `start/end` ضلت شغالة كخيار أبسط.

⚠️ **`workingHours` واحدة لكل الأيام المفتوحة** — لا يدعم ساعات مختلفة حسب اليوم (مثلاً عيادة حقيقية اختبرناها فيها الثلاثاء لحد 7م وباقي الأيام لحد 6م). لعميل بساعات متغيّرة، خذ **أضيق نطاق مشترك** (هون: 9-6) حتى ما توعد بوقت مو موجود فعليًا — تحت-عرض التوفر آمن، فوق-عرضه مو آمن. توسيع الـschema لساعات لكل يوم تحسين مستقبلي لو احتجته.

## ذاكرة الزبون (آخر سؤال + تفضيلات)

كل زبون إله ملف دائم بـ `data/<clientId>/customers/<userId>.json` (تاريخ محادثة + `facts` يقرر البوت بنفسه حفظها عبر أداة `remember_customer_fact`). أقصى 20 معلومة محفوظة لكل زبون. ما في إعداد إضافي مطلوب.

## كاش الردود (توفير تكلفة DeepSeek)

أسئلة FAQ متكررة الصياغة (نفس السؤال بترقيم/مسافات مختلفة) بتترد من الكاش مباشرة بدون استدعاء DeepSeek — `src/services/replyCache.js`، بذاكرة السيرفر (مو ملف)، TTL افتراضي 12 ساعة (`REPLY_CACHE_TTL_HOURS`) وحد أقصى 500 عنصر (`REPLY_CACHE_MAX_ENTRIES`). طفّيه بـ `REPLY_CACHE_ENABLED=false` لو احتجت.

**نطاق آمن ضيق عمدًا** — الرد ينخزّن/ينسترجع بس لو الثلاثة شروط مجتمعة:
1. الزبون "أول تواصل" (بدون تاريخ محادثة ولا معلومات محفوظة عنه) — حتى ما ينسرب سياق زبون تاني.
2. الرد ما استخدم أي أداة (حجز، فحص توفر، تذكّر معلومة) — حتى ما نخزّن جواب مرتبط بلحظة زمنية أو بزبون محدد.
3. الرد بدون تصعيد — حتى ما نعيد إطلاق إشعار تلقائي بكل cache hit.

يعني عمليًا: أسئلة عامة ("شو ساعات الدوام؟"، "وين عنوانكم؟") بتتخزّن، وأي شي فيه حجز/سعر/توفر لحظي ما بيتخزّن أبدًا — التحقق شغال حي، الفرق قياسًا: ~5ms (كاش) مقابل ~2000ms (استدعاء DeepSeek فعلي).

## سقوف الرسائل والعدّ

سلسلة الحواجز موحدة بين القناتين بـ `src/services/messageGate.js`:
- **حواجز ثابتة** (على كل رسالة): بوت موقوف → قناة مطفية → باقة بدون ودجت.
- **عدادات وسقوف** (بس قبل استدعاء DeepSeek فعليًا): trial → جلسة/ساعة (الودجت) → يومي → شهري/باقة.

ردود الكاش وكلمات التصعيد الجاهزة **ما بتستهلك من السقوف** — تكلفتهم صفر، فما منطقي تحسبها فاتورة. سقف التجربة مفحوص على القناتين (واتساب كان ناقصه سابقًا).

## بث ردود الودجت (streaming)

الودجت بيطلب SSE تلقائيًا (`Accept: text/event-stream`) والرد بيظهر تدريجيًا — أول كلمة خلال لحظات بدل انتظار التوليد الكامل. أي فشل بالبث بينزل تلقائيًا للمسار العادي بدون أي تدخل. طفّيه بـ `WIDGET_STREAMING=false`. ملاحظة نشر: الهيدر `X-Accel-Buffering: no` مبعوت مع كل رد بيثطّل nginx يمرر الدلتا فورًا بدون إعداد إضافي.

## الرسائل الصوتية على واتساب

البوت بيقرا رسائل واتساب الصوتية ويرد عليها: الويبهوك بينزّل الميديا من Graph API وببعتهل مزود تحويل متوافق مع OpenAI (Groq Whisper موصى به — `TRANSCRIBE_API_KEY` بـ.env) والنص يدخل نفس مسار المحادثة. فشل التحويل = رسالة اعتذار مهذبة، والخدمة مطفية تمامًا بدون مفتاح.

**تحكم وسقوف:**
- العميل (أو الأدمن) يقدر يعطّل الميزة كلياً من `voice.enabled` بـconfig.json — بدون مفتاح ولا سقف بيشتغل شي.
- **سقف دقائق شهري لكل باقة**: Starter ١٥ دقيقة، Growth ٤٥، Pro ١٢٠، التجربة ٥ (`TRIAL_VOICE_MINUTES`)، عملاء يدويين بدون tier بلا سقف.
- الفحص **قبل** تنزيل الميديا ونداء Groq (من حقل duration تبع Meta) حتى ما ينصرف مصروح على طلب راح يُرفض.
- عداد الثواني دائم على Firestore (`voice-seconds-monthly:<id>`) — ما بينصفّر مع restart.

## شحن رصيد رسائل إضافية (top-up)

العميل يقدر يعبّي حسابه برصيد محادثات إضافية لما يقرب على السقف، بسعر أعلى عمدًا من سعر الرسالة داخل الباقات ($0.080/$0.070 مقابل $0.058/$0.039/$0.020) حتى يبقى الاشتراك الخيار الاقتصادي:

| الباقة | الرصيد | السعر |
|--------|--------|-------|
| صغير | 100 رسالة | $8 |
| متوسط | 300 رسالة | $21 |

- الشحن يتم حالياً يدوياً: الأدمن يسجل الدفعة ويضغط "⚡ اشحن رصيد" بلوحة التحكم → الرصيد ينضاف لـ`topUpCreditsRemaining` + سطر بـpaymentHistory.
- الاستهلاك: الرصيد overflow فقط — بينستهلك لما السقف الشهري أو التجريبي يبلش يمنع، رسالة رسالة. الحد اليومي المضاد للإساءة ما بينتجزع منه.
- التحقق من الدفع لسا يدوي (بدون بوابة دفع) — نفس تدفق تسجيل الاشتراكات.

## قناة Telegram

لكل عميل بوت تلغرام خاص: يصنعو من @BotFather بدقيقة، والأدمن يحط التوكن من لوحة الأدمن (حقل `telegramBotToken`) — السرّ بتاع ويبهوك بيتولد تلقائيًا والتسجيل بيصير لحالو عند الإقلاع أو بعد حفظ التوكن. الطلبات المزورة بينرفضها بـ`X-Telegram-Bot-Api-Secret-Token`. يتطلب `PUBLIC_BASE_URL` https.

## تذكير المواعيد الاستباقي

فعّله لعميل بإضافة:

```json
"appointments": {
  "enabled": true,
  "workingHours": { "start": "09:00", "end": "17:00" },
  "reminders": {
    "enabled": true,
    "hoursBefore": [24, 2],
    "templateName": "appointment_reminder",
    "templateLang": "ar"
  }
}
```

- **مع `templateName`** (قالب معتمد عند Meta بنص مثل: `تذكير: موعدك يوم {{1}} الساعة {{2}} مع {{3}}.`): إرسال بأي وقت — هاد المسار الصحيح.
- **بدون قالب**: نص حر بس لو الزبون راسلنا خلال آخر 24 ساعة (نافذة خدمة Meta)، غير هيك بينتجّز مع تحذير بالسجل.
- الفاحص بيشتغل كل 5 دقائق، وكل عتبة ساعات "بتملك" نافذتها (24h تشتغل بين 24 و2 ساعة قبل الموعد، 2h بين ساعتين وصفر).

## قناة Discord

نفس نمط تلغرام: توكن بوت لكل عميل (حقل `discordBotToken` من لوحة الأدمن) — بس الاتصال عبر **gateway websocket دائم** بدل ويبهوك (`services/discordGateway.js`، بدون discord.js). الرسائل الخاصة (DM) فقط بهالمرحلة. **شرط تشغيلي:** فعّل "Message Content Intent" من بوابة مطورين Discord لكل بوت وإلا النصوص بييجوا فاضية. إعادة الاتصال تلقائية بـbackoff أسي.

## رد آلي خارج ساعات الدوام

فعّله من لوحة الأدمن (خانة "تفعيل رد آلي خارج الدوام" + ساعات من/إلى) أو `businessHours` بـconfig.json. الرد مهذب مع توجيه للتواصل المباشر، بدون استهلاك DeepSeek ولا عدّ بالسقوف — وكلمات التصعيد بتتجاوزو عمدًا ("بدي حدا حقيقي" برا الدوام توصل لصاحب العمل).

## سجل وتصدير المحادثات

كل تبادل بينتحف كاملًا ودائمًا بـ`data/<id>/transcripts/<userId>.jsonl` (السياق المرسل للنموذج مقصوص بـ8 أدوار، بس السجل الكامل مو). صفحة إدارة البوت فيها قسم "المحادثات": لائحة الزبائن، عرض محادثة كاملة، و**تصدير Excel** (ملخص + كل التبادلات).

## تخصيص الودجت

من لوحة الأدمن: لون الهوية، عنوان مخصص، وحتى 4 أسئلة مقترحة تظهر كأزرار فوق حقل الإدماج (بتنضغط مرة وبتبعت). الودجت بيجيب الإعدادات تلقائيًا من `/api/v1/widget-config/:clientId` عند أول فتح — أي فشل صامت والإعدادات المضمّنة بالوسوم بتضل هي الأساس.

## إحصائيات المشغّل والتكلفة

عدادات يومية دائمة (`data/stats.json`: رسائل/نداءات LLM/إصابات كاش/تصعيدات/توكنز) + التقاط usage فعلي من DeepSeek (حتى بالبث عبر `stream_options`). قسم التحليلات بلوحة الأدمن بيعرض رسم آخر 14 يوم + تقدير تكلفة الشهر بالدولار (أسعار قابلة للتعديل: `DEEPSEEK_PRICE_*_PER_M`).

## المعرفة الكبيرة (استرجاع أولي بدل الحقن الكامل)

المعرفة ≤ 12 ألف حرف تنحقن كاملة بكل رسالة (سلوك الأغلبية). الأكبر من هيك: بتتقسم أجزاء عند حدود الفقرات، وبكل رسالة بينختار الأجزاء الأقرب لسؤال الزبون بتطابق معجمي بعد تطبيع عربي (همزات/تاء مربوطة/تشكيل) — `src/services/knowledgeRetrieval.js`. هاد بيرفع السقف العملي للمعرفة بدون RAG دلالي كامل (embeddings تحتاج مزود إضافي — DeepSeek ما بيقدمها).

## ملكية رقم واتساب — مين بيعطي شو

الرقم لازم يكون مسجّل تحت WhatsApp Business Account (WABA) بمنصة Meta:

1. **الأسرع للبداية**: تسجّل رقم العميل تحت Business Manager تبعك إنت — بس بيعطيك رقم مخصص، وتحط `phone_number_id` الناتج بـ `config.json` تبعه يدويًا.
2. **أنضف على المدى الطويل**: العميل يسوي حساب Meta Business Manager تبعه هو ويعطيك صلاحية وصول (embedded signup).

ابدأ بالطريقة 1 لأول 3-5 عملاء (حساب غير موثّق كافي لـ 250 محادثة/24 ساعة). التسجيل الذاتي بيدعم ربط واتساب تلقائيًا عبر **Embedded Signup** (زر بصفحة onboard — يحتاج `META_APP_ID` + `META_APP_SECRET` + `META_EMBEDDED_SIGNUP_CONFIG_ID`).

## نشر السيرفر (deploy)

يشتغل على أي مكان يستضيف Node.js (Railway، Render، VPS رخيص). لازم HTTPS ثابت + `PUBLIC_BASE_URL` مضبوط صح (بيروح براوابط تأكيد الإيميل وكود الودجت الجاهز).

## ملاحظات أمان

- `.env` وملفات `data/` (فيها `signups/`, `customers/`, `appointments.json`) ما بينرفعوا لأي مكان (`.gitignore`) — فيها بيانات شخصية حقيقية.
- **ويبهوك واتساب محمي بتوقيع** `X-Hub-Signature-256` (HMAC بـ`META_APP_SECRET`، فشل مغلق) — بدون السر مضبوط، الويبهوك بيرفض كل الرسائل.
- `/docs` انشال من السيرفر (2026-08-22) — كان يعرض خططا داخلية للعامة.
- `WEB_WIDGET_KEY`/الوضع القديم مو أمان حقيقي (ظاهر بمصدر الصفحة + مفتاح واحد لكل العملاء) — استبدله بـ `pk_` لكل عميل أول ما تقدر وطفّي `ALLOW_LEGACY_WIDGET_KEY`.
- `urlGuard.js` بيمنع SSRF (روابط داخلية/محجوزة) لما "استورد من موقعي" بيجيب رابط من مستخدم خارجي — حد معروف: نافذة نظرية لـ DNS rebinding (راجع تعليقات الملف).
- مكتبة `xlsx` الأصلية عندها ثغرات أمنية بدون حل — استبدلناها بـ `exceljs`. تحذير moderate متبقي بتبعية `uuid` غير مباشرة (نمط استخدام غير مرتبط بيلي عنا).
- **قبل ما توصل بوت لأول عميل حقيقي**: راجع نقطة "الهلوسة والمسؤولية القانونية" من قرار المجلس (`council-report-20260804-225516.html` بمجلد `new app work`) — حط بند تعاقدي واضح يحدد مين مسؤول عن غلطة البوت. للعملاء اللي بيجوا عبر التسجيل الذاتي تحديدًا: `knowledgeReviewed: false` وتحذير بالـ system prompt بيقللوا الخطر (البوت بيصعّد بدل ما يخمّن)، بس مو بديل كامل عن المراجعة.

## معروف ناقص (مؤجّل عمدًا)

- **توثيق API رسمي** (`/docs` OpenAPI + Redoc/Scalar): مؤجل لحد أول شركة تطلب تكامل برمجي مباشر (مو بس الودجت الجاهز).
- **`sk_` endpoints** (`/appointments`, `/usage`): مؤجّلة لحد أول عميل يطلب وصول برمجي فعلي لبياناته.
